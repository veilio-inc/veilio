# What veilio-guard covers, and what it does not

This is the statement Veilio publishes about the Claude Code guard. Each claim names the test that holds it; `tests/guard/coverage.test.ts` fails if a test named here is missing. The "Not covered" list states what the guard cannot do.

It applies to Claude Code 2.1.287 or later, with the plugin installed and its mod loaded. That means the terminal CLI, the Code tab of the Desktop app, the VS Code extension's chat panel, `claude -p` and the Agent SDK. Under `claude -p` and the Agent SDK what Claude reads is guarded the same way, but its reply is not restored: see "Headless replies" under Not covered. Other agents (Cursor, GitHub Copilot, Codex) are not covered by this plugin. Tested on macOS and in Linux CI, and in one Windows 11 session on 2026-10-07 (the terminal CLI), described under Covered. That session predates the PowerShell rule of guard `0.6.0`, which has not been run on Windows.

## Covered

The interactive walk in a terminal was done on 2026-10-03 (the band, the redrawn replies, tool rows and diffs, `/veilio`, and the transcript on disk holding placeholders only). On Windows, one session on 2026-10-07 (Windows 11, the terminal CLI) found that Claude Code's PowerShell tool had none of the shell checks; it now gets every check Bash gets. The rest of that session passed.

## Not covered

- **Without the mod, nothing is guarded.** That includes Claude Code before 2.1.287, a session started with `--safe-mode` or `--bare`, and your own `disableAllHooks` setting (the guard refuses the agent writing it into Claude Code's settings files; a program the agent runs can still write them). In those cases Claude reads raw code. An organisation that runs the guard through managed settings keeps it running under a user's `disableAllHooks`.
- **The first message on a project with no map.** Names you type are masked once the index has reached the file that declares them, which on most projects is before the first message is sent. Until then, names you type go to the model as you typed them; what you type is not shape-masked, because you may be quoting something on purpose. Running `veilio scrub` on the project first builds the map ahead of the session.
- **Names in files the index does not reach.** The guard indexes the project's tracked source files (`git ls-files`) when a session starts, and before any result the files that result names. A name that appears only in output from somewhere else (an untracked or generated file, a dependency) is masked when it is shaped like an identifier (`luhnValid`, `team_layers`, `BatchReconciler`). A lowercase one-word name from there (`settle`) passes as written.
- **Results while a large project is indexed.** Indexing runs for about 6 seconds as the session starts, then in short slices between calls (veilio-cloud, 690 files, needs about two hooks' worth of time). A result that names a file not indexed yet waits for it within its own budget, and is withheld if that runs out. On a large project the first results of a session can be withheld.
- **Which packages count as third-party.** Only public-looking ones: an unscoped npm package, a Python module that is not in the project, and the Go standard library. A scoped package (`@acme/ledger`) and any Go module with a host (`github.com/…`, `git.corp/…`) are treated as the project's, because a company publishes its own code that way; their names stay masked. No name is exempted in a project that also has source in a language whose declarations Veilio does not read (anything but TypeScript/JavaScript, Python and Go; shell scripts do not count, as they declare nothing those import), or while a file could not be indexed.
- **Flags.** Only in what you type: a flag-shaped word after a space and a dash or two, which the map holds only as a path or a string. In tool results nothing is exempt for following a dash, so negation, decrements and diff lines are masked.
- **Third-party names early in a session.** They are left as written only once the whole project is indexed (about 6 seconds into a medium project's session). Before that they are masked like the project's own names, which costs readability and leaks nothing.
- **One-word values in records.** In a structured result (a tool's record, an MCP result), a string that is one bare token is a field's value, such as a status or an enum, and the identifier-shape fallback leaves it, because Claude Code refuses a record whose enum changed. A declared name there is still masked through the index and the map.
- **Programs that open files themselves.** The raw-only check reads the words of a command as bash and zsh would, but does not run them, and it does not follow a value through a variable. So it stops ordinary and accidental reads, and these get through: a name or part of one carried by a variable, also when the variable is set in the same command (`a=.e; b=nv; cat $a$b`, `cat "$1"`), the name of a shell setting put together the same way (`a=GLOB; b=IGNORE; export $a$b=y`), the shell itself named through a variable when its script holds a zsh group Veilio cannot read exactly (`x=zsh; $x -c 'cat .e(n*)v'`), and an option a shell is given through a variable (`echo 'cat *nv' | bash $opts`; an option written with its dash, as in `bash -$x`, is refused); what a command prints (`.e$(echo n)v`, `ls | xargs cat`, `curl … | sh`); a script that opens `.env` itself, also one the command has just written to a file; a program Veilio does not know as a shell, given options of its own and a script on a pipe (`echo 'cat *nv' | ./mysh -O dotglob`); `grep -r`, `tar` or `cp -R` over a folder that holds such a file among others (`grep -r KEY .`, `cp -R ~/.aws a`); a path part that is only wildcards (`cat *`, `cat */customers.csv`); and a wildcard at the end of a word against a pattern such as `*.pem` (`cat server.p*`). A whole name in an assignment is still refused (`F=.env; cat $F`), and so is a folder that holds only raw-only files (`grep -r KEY secrets`, `cp -R ~/.veilio x`). Credentials in what it prints are removed, but plain values such as a database host are not. A copy or an archive prints nothing, so nothing is removed from it. Strict mode, a later release, will close this with an operating-system sandbox. Such a program can also print a source file's names reshaped - re-cased, split across other text, or encoded in a form the guard does not decode - and those reach the model in that form. Windows streams and short names are tested only as text, on macOS and Linux.
- **Tests the agent writes.** A placeholder is restored only into read/test commands; a test the agent wrote can still reshape or send it - closed only by strict mode / not covered. An edit lands with the real names, and a test runner runs it: such a test can print a name encoded or send it over the network. The guard withholds output that holds a removed credential in a reshaped or encoded form and a project name as base64, hex, reversed or spelled down a column, but not a name or key sent out, written to a file, re-cased or encoded any other way: a name spelled out by `od -c`, folded into lines of four characters or more (`fold -w5`), or printed as base64 glued to the end of a path (`build/UGF5…`) reaches the model.
- **Resumed sessions outside git.** Outside a git checkout, only placeholders the current session showed are restored. After `claude --continue` or a restart, an edit or command that uses a placeholder from the earlier session is refused until the file is read again.
- **Where the shell is.** The guard keeps the directories the shell may be in, through each command of a call and into the next call: a cd joined by `&&` moves it, one after `||` or `;` may have, one in a subshell, `$( )` or a pipeline stage ends there. A call starts where Claude Code reports the shell is, once that report has proved live (it named a directory a cd the guard saw led to); where the report and Veilio's own reading of the last command differ, both are checked, and a call past the bound is refused. Until the report proves live, every directory a call may have left the shell in is carried. In PowerShell, which keeps one location for the session, a pipeline stage, `$( )` and a script block move it too. A short name is checked in each of them. A directory change made by a script (`./build.sh`, `source env.sh`) is not followed.
- **Clearing the map while a session is open.** The guard puts back every entry it knows on its next save, so `veilio map --clear` run while Claude Code is open is undone. Clear the map with no session open.
- **Two programs saving the map in the same instant.** The guard reads the file, merges and writes it, but Claude Code gives a mod no atomic write. Entries another program drops are put back on the guard's next save, and a placeholder that would mean two names is detected and masked again.
- **Lowercase words from string literals.** A one-word, lowercase string literal (`'the'`, `'keep'`) is masked only inside source files, where the engine finds it in a literal. In output, prompts and comments it is left as written, because masking it there turns a git log into placeholders. That includes a lowercase one-word name written in a literal, such as a surname, a codename or a one-word host name: inside its source file it is `__STR__n`, and anywhere else the model reads it. A capitalised literal word (`'Contoso'`) or one shaped like a name (`'customer_refunds'`, `'apiV2'`) is masked everywhere. Code names that are a single common English word (`total`, `update`, `ledger`), shared vocabulary (`src`, `util`, `com`, `java`) or a toolchain's name (`vitest`, `junit`) are not masked as names or path segments, from spec 064 on (in a value they are, round 3): they are nobody's secret, and masking them turned paths and test output into placeholders the model could not navigate. A codename that is an ordinary word (`phoenix`) is therefore readable too, unless a custom replace rule names it: pulled with `veilio rules pull`, the rule masks it in the guard as in the CLI.
- **Prose in comments.** The engine masks identifiers. Comment text is left as written, apart from names the map already has.
- **A failing failure handler.** If the `.catch` handler itself fails, Claude Code keeps the tool's result. The handler returns a constant and does no work, so this is not expected.
- **Timeouts.** A scrub that overruns Claude Code's 10-second budget takes the same `.catch` path as one that throws. The kit can't force a timeout in a test, so there is no test of its own. Reading a command before it runs has a budget of its own, far below that: a command the guard cannot read within it is refused (`reading-cost.test.ts`).
- **Headless replies.** In `claude -p` (text, `--output-format json` and stream-json) and in the Agent SDK, Claude's reply, the printed result and every assistant message keep the placeholders: nothing draws them, and the real names are drawn only where Claude Code draws a reply (the terminal, the Desktop app, VS Code). Claude Code 2.1.310 offers a mod two other routes, and both put real names where the guard keeps them out: an answer from a `turn.complete` hook does not replace the printed result and is stored as a notice in the session's transcript file on disk, and a `session.append` rewrite is what the next request sends to the model. To read a headless reply with the real names, restore it on your machine with the project's map: `claude -p "…" | veilio restore`. The founder decided against an opt-in restore inside the guard for headless runs (it would write real names into the transcript file); piping through `veilio restore` is the way.
- **A weak password away from its assignment.** The guard carries forward, for the rest of a session, only credentials with structural signal: provider-format keys, high-entropy strings and long mixed-class strings. The value of a credential-named key that only the guard removes is carried forward when all of these hold, whichever tool showed it (a search result too, when its lines' files can be told apart - see Search output read by file): the key the engine matched names a secret - its last part is `password`, `passwd`, `pwd`, `pass`, `passphrase`, `secret`, `token` or `apikey`, or its last two parts are `api`, `private`, `access`, `secret`, `encryption` or `signing` and then `key`, read across camel case, `_`, `-` and `.`, with a trailing number or version allowed (`DB_PASSWORD=…`, `DB_PASSWORD_2=…`, `API_TOKEN_V2=…`, `"secretKey": "…"`, `"client_secret": "…"`, a client token such as Vault's `"client_token": "…"`, `SMTP_PASS=…`, a k8s `name: DB_PASSWORD` with its `value:`), but not a flag (`is_secret: …`, `has_password: …`), not a token that is a cursor or a request id (`NextToken`, `nextPageToken`, `PaginationToken`, `continuationToken`, `syncToken`, `resumeToken`, `changeToken`, `cursorToken`, `StartingToken`, `idempotencyToken`, `cancellationToken`, `skipToken`, `deltaToken`, `pagingToken`, `resumptionToken`, `afterToken`, `scrollToken`, `lockToken`, `etagToken`, `previousToken`, `prevToken`, `continueToken`, `requestToken`, `csrf_token=…`, `XSRF-TOKEN`), not a key with a `checksum`, `hash` or `digest` part (a Helm `checksum/secret:` annotation), not a lookup call whose first part is `get`, `fetch`, `read`, `load`, `lookup` or `find` (`client.getSecret('stripe-key')`, `keyring.get_password(…)`: the argument is a name; `setPassword('…')` is given the secret), and not a bare `token`, `pass`, `pwd` or `secret` (`PWD` is the working directory, a k8s `secret:` names a resource; `SECRET_KEY=…` and `APP_SECRET=…` are secrets); the value is a literal - quoted, or found by a configuration grammar (an env, ini, shell or YAML line, a k8s env entry, an XML element, a .pgpass line, or a `KEY=value` written tight in a URL or a connection string) in text that is not code. In a file of a known language - a Read, Edit, Write or MultiEdit of it, a command that prints it - only a quoted value is carried forward: a configuration-shaped line there is an assignment (`self.secret_key = rotateKeyV2`, `this.apiKey = …`). Outside code, an unquoted value on a line of its own is a configuration line, so a strong `password = …` there is carried forward; one inside a statement (`const password = …;`) is not; the value is not a reference: it does not start with `$`, quoted or not, holds no `${` or `$(` anywhere (`${DB_PASSWORD:-}`, `${env:X}`, `$(vault read …)`), and is not wholly a template's placeholder (`%(name)s`, `%NAME%`, `#{name}`, `{{ name }}`, `${{ … }}`), not an encrypted value (`ENC(…)` and `enc(…)` from Jasypt, `ENC[…]` from SOPS, `{cipher}…` from Spring, Mule's `![…]`, AWS KMS ciphertext starting `AQICAH`, a Sealed Secret starting `AgB` of 200 base64 characters or more), not an AWS resource name (`arn:…`, a KMS key under `EncryptionKey:`), not an environment variable's name (`password: GITHUB_TOKEN_CI2`, `SECRET_KEY_V2`, judged as in A variable's name as a value below, with a trailing `_V2` read as a number), and not a lowercase kebab-case name (`db-password-v2`, `postgresql-password-2`: a resource's name, like decision #5's weak values) - each of these is removed where it stands but not carried forward, and so is a literal password that starts with `$`, a known limit; it holds no redaction token (a provider key the scanner found inside it keeps its own token, and what follows a `&`, `,` or `;` after it stays as written); it is 16 KB at most; and it passes the scanner's own bar above. An unquoted value is carried forward also without what follows a `&`, `,` or `;` (`access_token=…&state=1`, `Password=…;Database=app`), and its slot takes that shorter value's token, or the whole value's when only that is strong. In a search result (the Grep tool, or one plain `rg`/`grep` in a shell) only the lines whose file the guard can name from the files on disk teach the key rule, each in its own file's kind (in a source file only quoted values); a line it cannot place teaches nothing and is masked line by line as before (see Search output read by file). A key's value that holds a redaction token is removed whole - what follows the token in it can be another credential - and only its clean parts are learned. Such a value is removed from every later result, and never saved to the map as a name. Every other value of a credential-named key is removed only where it stands: one under a key that merely contains a credential word (`AUTH_PROVIDER=…`, `auth_method: …`, `"tokenizer": …`, `apiKeyName`, `sortKey`, `pass_through_tag=…`), a weak one (`DB_PASSWORD=sunshine2026`, a word and a year), and one over 16 KB (work queue e72). A low-entropy password (`my-secret-pass`, `hunterpassword`) is redacted where its rule finds it, after `password =` or in a connection string, but if it appears bare somewhere else in the session it is sent as written. Where a weak password most often reappears the engine now finds it where it stands, whatever its strength (spec 013, decisions 5 and 6): a password flag on a command line (`mysql -p<pw>`, `--password <pw>`, `sqlcmd -P <pw>`, `redis-cli -a <pw>`), a password environment variable (`PGPASSWORD=`, `MYSQL_PWD=`, `POSTGRES_PASSWORD:` and others), URL userinfo, and an auth header (`Authorization: Bearer` from 8 characters, `Basic` of any length, `X-Api-Key`, curl `-H` and `-u user:pass`). Port flags (`mysql -P 3306`, `psql -p 5432`) are not passwords. A token carried as the user (`https://<token>@host`, curl `-u <token>:`, a provider key in decoded Basic credentials) is redacted in every file; a plain user name is kept. The engine only reports a weak value there when its caller names a test, fixture or example file; the guard names none, so it redacts these in every file, test files included. A copy of `.env` in `tests/` cannot be told from a committed fixture safely enough to leave its passwords in place (spec 013 R16), and the CLI and the MCP server read every file strictly too. A value plainer still is not redacted even there: the engine only reports a value in a credential slot whose entropy is below its floor (`secret = "11111122222233"`, `password = "aaaabbbbcccc1"`) or that is one lowercase word (`password: 'required'`), because such values are almost always dummies, defaults or modes, and redacting them for good would corrupt code; it is reported to you, and sent as written. The released engine does the same. A low-entropy string with no structural marker is an ordinary word: every rule that swept such values everywhere also blacked out the project's own words (remembering every value and removing it as a whole token blacked out `required` after `{ password: 'required' }`, and `postgres` after a docker-compose URL), and every rule that spared the words leaked some passwords. An automated review that flags "weak password not swept" is pointing at this entry. This is the founder's decision #5 (spec 013, research R4). Guard 0.2.0 carried nothing forward, so this is still stricter than the release. A test pins it: `scrub.test.ts` (lib) › a weak password seen bare away from its assignment is not swept: the documented limit; for a credential-named key, `scrub.test.ts` (lib) › a value under a credential-named key is learned only when the scan would learn it, › a strong value under a key that only contains a credential word is not learned, and `results.test.ts` › a weak value redacted after its credential-named key is not swept from later results.
- **A variable's name as a value.** A value that is an environment variable's name or another all-caps reference (`'google-api-key': 'GOOGLE_KEY'`, `password = "AWS_SECRET_ACCESS_KEY"`) is left as written, even after a key that reads like a credential's: it names where the secret lives and is not one. It is masked only if the map holds it as a name. The value must be made of known words: upper case with at least one `_`, every part a word from the guard's list of environment-variable words (`ENV_NAME_WORDS` in lib/scrub.ts, about 230 words such as API, KEY, SECRET, DATABASE, URL, REGION, PORT) with optional digits after it, or one number of four digits at most (`DATABASE_URL`, `STRIPE_SECRET_KEY`, `API_KEY2`, `AWS_REGION_2`, `PORT_8080`). A part not on the list means the value is not a name and it is redacted, as before decision 2: shape cannot tell random letter blocks from words (`XQAE_ZPOW_KIVR_TUYM`, `KXEQ_ZUVW_PYOT_RAIM_QOEX`, `X7K9A2_Q2LE4M8P` are credentials). A bearer, basic-auth or connection-string value is never exempt (`Bearer ABCDEF_GHIJKL_MNOPQR` is a token). This is the founder's decision 2. A test pins it: `scrub.test.ts` (lib) › an environment variable name used as a value is left as written.
- **What removing a credential costs.** A value Veilio destroys takes with it, in its slot, every key character that runs on after it. Elsewhere it is removed wherever it appears: an identifier that holds a password reads as a name built around a redaction token, and an edit that would write the token back is refused. A low-entropy password (`postgres`, `my-secret-pass`) is removed only where its rule finds it, and one too plain for the engine to call a credential is only reported (see A weak password away from its assignment). Credentials are learned in the order the session shows them: a text masked before the one that reveals a credential is not masked again. The session's credentials live in memory only, so token numbers start again after Claude Code restarts, and a value under six characters (a short database password in a URL) is removed only where its rule finds it, with that scan's own numbering.
- **Placeholders the CLI made during a session.** The guard cannot tell `veilio scrub`'s output, or a file it scrubbed, from any other text that already holds placeholders, so a placeholder the CLI minted while a session is open is refused for the rest of that session (it was not shown by the guard); the next session restores it. Veilio's MCP server is told apart by its tool name.
- **Commands the guard cannot read.** The guard reads a command's words as bash and zsh would, but does not run the shell or sandbox it. It is there to stop ordinary and accidental reads; a command written to get past it can (see "Programs that open files themselves"). A script's own commands (`source env.sh`, `./build.sh`) are outside what it promises, and so are PowerShell spellings beyond quotes and the backtick, and shells other than bash and zsh. A bash or zsh command it cannot read - a shell started with options or input it does not know, a zsh module loaded in the command, a command over 100,000 characters, or one that takes more work to read than its budget allows (more than about 2,500 different paths, hundreds of bracket lists in one word, tens of thousands of words to judge; long text that a program only stores does not) - is refused. A PowerShell command it cannot read is refused when it could move the shell or run text as code, and runs otherwise.
- **The shell's own startup.** Claude Code runs each Bash command after a snapshot of your shell setup from your startup files (aliases, functions, options), and zsh also reads `~/.zshenv`. What those set - CDPATH, `cdable_vars`, an alias or function that changes directory - is not seen when the guard reads a command; the directory Claude Code reports at the next call is.
- **Known false positive: a cd after inline code.** A call that runs an interpreter's inline code and then changes directory (`python3 -c "…" && cd src`, `node -e "…"; cd packages/cli`) is refused, since that code could have made a link. Run the cd first, or in a separate call.
- **Environment carried between calls.** The Bash tool runs each call in a fresh shell that keeps only its directory, so HOME and CDPATH are judged per call. An export that a Claude Code mechanism carries into later calls (`CLAUDE_ENV_FILE`, a SessionStart hook that sets the environment) is not seen.
- **Teammates' values in edits.** Edit and Write content gets a teammate's map values back as written; only commands and MCP arguments check their shape.
- **Images, audio and documents attached to a prompt** are sent as they are: the guard cannot read their contents, and says so the first time in a session. An image or PDF that Claude reads with a tool is withheld.
- **Images and PDFs that Claude reads with a tool** are withheld, not scrubbed. One attached to your prompt is not: see above.
- **What a slash command records for the model.** Claude Code does not let a mod change the notes a command leaves the model beside its output, so they reach the model as the command wrote them.
- **Names with letters outside A–Z.** Names that contain letters outside A–Z are not yet masked whole. A name written only in Greek or Cyrillic letters (for example `παραγγελία`) is not masked at all. A name that mixes A–Z with other letters (for example `wyślijPaczkę` or `größeBerechnen`) is masked only in its A–Z parts, so the other letters reach the model. Names written only in A–Z are not affected. Until this is fixed, rename such names, or leave files that use them out of what you send. Full support is planned for the next release (#224).
- **Project instructions in the stored transcript.** A Windows session on Claude Code 2.1.292 found CLAUDE.md's text stored as written in the transcript's `instructions` record on disk, while Claude received it masked. The guard rewrites what Claude is sent; it has no hook into the record Claude Code stores on your machine. Not reproduced headless on macOS with 2.1.289 or 2.1.292. Keep real names you would not want in local session files out of CLAUDE.md, or name them with placeholders.
- **Claude Code's own fixed texts.** Some texts Claude Code adds itself, such as the advisor tool's instructions, do not pass through the guard's hooks. They hold no project code, but a project name that is also an English word (`reconcile`) can appear in them as written.
- **Search output read by file.** A search result's line is read with its file only when exactly one way of reading its prefix names a regular file on disk, from the session's working directory (the Grep tool's paths) or as an absolute path. Everything else is masked line by line as before, with no pairing across lines and nothing learned from the key rule: a line whose file is not on disk or not a regular file, a path that climbs out with `..`, a Windows path on another machine, two prefixes that both name files, a prefix past a line's first 4 KB or a line with more than 16 candidate separators, lines past the 512th file check of one result, `--heading` and `--json` output, a shell search in a pipeline or after `cd`, every shell search after a command in the session changed the shell's directory (`cd`, `pushd`, `popd`, also in a command that failed), and a search whose reading does not finish within the hook's budget. Without line numbers and context lines, matches are judged one line at a time (they need not be neighbours in the file). Once a file is placed in a result, a later line that starts with its path is placed in it too without checking for a file whose name extends that path with `:` or `-`. A YAML block scalar (`password: |` and lines below) has only its first line read as the value, as in a Read. A file named for a secret that is not confirmed as one value (more than one line, a value with spaces, unreadable, or not read in time) is masked as before, by its path: a value with spaces only up to its first space. Measured on a corpus of 969 search results against the guard before this (`tests/guard/search-differential.test.ts`): no redaction lost, no result withheld, and every result with nothing to read by file byte for byte the same.
- **Searches reveal parts of names.** A search for a word matches inside the real names, so a match on a line where Claude sees only placeholders tells it that one of those names contains the word (`grep settle` matching the line of `settledTotal`). The names themselves stay masked.
- **What Claude says it saw.** Your view is redrawn with the real names, so when Claude explains that it only sees placeholders, the placeholder it quotes is drawn as the real name too. Ask it to spell the name letter by letter to see what it received.
